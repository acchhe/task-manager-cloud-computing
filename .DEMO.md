# Task Manager - Demonstration Plan

## 1. Project Introduction

Task Manager is a cloud-native application built using Python, FastAPI, MongoDB, Docker, and Kubernetes.

The application consists of two independently scalable REST API microservices and a persistent database.

## 2. Kubernetes Deployment

Show the running Kubernetes Deployments using:

`kubectl get deployments`

Expected configuration:

- Task Service: 2 replicas
- Statistics Service: 2 replicas
- MongoDB: 1 replica

## 3. Task Service Demo

Open:

http://localhost:8000/docs

Demonstrate how to create a new task using the POST /tasks endpoint.

Verify that the task appears in GET /tasks.

## 4. Statistics Service Demo

Open:

http://localhost:8001/statistics

Show that the statistics reflect the tasks stored in the application.


## 5. Independent Scaling Demo

Task Service and Statistics Service can be scaled independently in Kubernetes.

### Scale Task Service

Increase Task Service from 2 to 3 replicas:

```powershell
kubectl scale deployment task-service --replicas=3
```

Verify the result:

```powershell
kubectl get deployments
```

Task Service should now have 3 replicas, while Statistics Service still has 2 replicas.

### Restore the Original Configuration

Scale Task Service back to 2 replicas:

```powershell
kubectl scale deployment task-service --replicas=2
```

This demonstrates independent scaling of microservices in Kubernetes.

## 6. Persistent Storage Demo

MongoDB uses a Kubernetes PersistentVolumeClaim (PVC) named `mongo-pvc`.

The PVC provides persistent storage for task data.

### Verify Existing Data

Open the Task Service endpoint:

http://localhost:8000/tasks

Verify that the task "Learn Kubernetes" exists.

### Delete the MongoDB Pod

Run the following command:

```powershell
kubectl delete pod -l app=mongodb
```

Kubernetes automatically creates a new MongoDB Pod because MongoDB is managed by a Deployment.

### Verify Pod Recovery

Run:

```powershell
kubectl get pods -l app=mongodb
```

Wait until the new MongoDB Pod shows `1/1 Running`.

### Verify Data Persistence

Open:

http://localhost:8000/tasks

Verify that the task "Learn Kubernetes" still exists.

### Result

The persistence test was successfully performed during development.

The task remained available after the MongoDB Pod was replaced.

This demonstrates that the PVC preserves database data across Pod replacement.


## 7. Architecture Overview

Show the architecture diagram located in:

`architecture/kubernetes-architecture.png`

Explain the three main components:

- Task Service: Manages tasks using a REST API.
- Statistics Service: Retrieves tasks and calculates statistics.
- MongoDB: Stores task data using persistent storage.

### Kubernetes Communication

Statistics Service communicates with Task Service using:

`http://task-service:8000`

Task Service connects to MongoDB using:

`mongodb://mongodb:27017/`

Kubernetes Services provide stable DNS names and distribute traffic between available Pods.

## 8. Security Considerations

The application uses internal Kubernetes networking for communication between components.

MongoDB is exposed internally through a ClusterIP Service.

Task Service and Statistics Service are accessible through LoadBalancer Services.

### Current Limitations

- The REST APIs do not require authentication.
- MongoDB authentication is not enabled.
- Communication uses HTTP instead of HTTPS.
- Kubernetes NetworkPolicies are not configured.

### Future Improvements

- Implement API authentication and authorization.
- Enable MongoDB authentication.
- Store credentials in Kubernetes Secrets.
- Enable HTTPS using TLS.
- Configure Kubernetes NetworkPolicies.

## 9. Conclusion

The project demonstrates a cloud-native application using Docker and Kubernetes.

It includes two independently scalable REST API microservices, internal service communication, and persistent database storage.
